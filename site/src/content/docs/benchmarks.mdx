These numbers compare this library with native `Array`/`Map`/`Set`, `js-sdsl`, `mnemonist`, collections.js and
`@datastructures-js/priority-queue`, including the cases where this library is slower.

## How the comparison is run

`npm run bench:isolated` is built so that no implementation can affect another:

- **One implementation per process.** Every (workload, implementation) pair runs alone in a fresh Docker container that
  loads only that package. This matters: collections.js replaces built-ins such as `Array.prototype.find`, `Object.is`
  and `Array.from` when it loads.
- **Same environment.** One image for all: Node.js v24.12.0, pinned package versions, and this library's published
  build (`dist/`). Each container is pinned to one CPU (`--cpuset-cpus 1 --cpus 1 --memory 2g --network none`).
- **Same data, same test.** Each workload has one seeded dataset and one test loop, written once in
  `bench/isolated/workloads.ts`; implementations plug in through a small adapter (`put`, `get`, `offer`, `poll`, ...).
- **Same answer.** Before timing, every implementation must return the same checksum on that data (for example the same
  number of LRU cache hits). The run stops if any disagrees.
- **Order and repeats.** Containers run one at a time in shuffled order, 3 or 5 times each; tables show the median.

Docker on macOS runs a Linux VM, so compare the ratios, not the absolute ops/s. Each ratio is relative to the baseline
named in the last column; >1.00× is faster. Run on 2026-10-21, Apple M1 Pro.

## Run it in your browser

Every workload below runs on your device: the same data, test and implementations, each in its own Web Worker. Next to
each of your ratios is the one the isolated run measured. Run all takes about two minutes.

## Why it is faster

- **Integer keys skip hashing.** `HashMap`, `HashSet` and the `LinkedHash*` variants store each key in the fastest
  storage that is still correct for it: integers in `0..2^30-1` go to a dense array indexed by the key (while it stays
  at least 25% full), primitives and plain objects go to a native `Map`, and only keys with `equals()`/`hashCode()` or
  `Date`s use a hash-bucket table. `LinkedHashMap` threads a doubly linked list through its nodes, so ordered
  iteration, `pollFirstEntry` and LRU moves are O(1).
- **`ArrayDeque` is a power-of-two ring buffer.** Wrapping is a bitmask, vacated slots hold a small integer so a deque
  of numbers stays in V8's fast numeric arrays, and removing from the middle shifts the shorter side.
- **`PriorityQueue` sifts a hole** instead of swapping (half the writes), compares with a plain `<` while it has only
  seen non-`NaN` numbers under natural order, and heapifies a source collection in O(n).
- **`TreeMap` is a red-black tree with parent pointers.** Iterators step to the successor without a stack, the maximum
  is cached (so `lastKey()` is O(1) and ascending inserts skip the descent), and number and string keys are compared
  inline.
- **Streams push, and fuse stages.** Without short-circuiting stages the source runs one tight loop; short-circuiting
  sinks flag cancellation upstream instead of being asked per element; consecutive `filter`s fuse into one stage, as do
  consecutive `map`s. `Array` chains allocate an intermediate array per stage, which streams do not.
- **`ArrayList` keeps a packed array** with no holes, so `get`, `set` and `push` compile to plain array accesses.
  That is also why its `initialCapacity` is validated but never used to preallocate.

## Where it is slower, and what to do

| Case | Measured | Why, and what to do |
| --- | --- | --- |
| `for..of` over `ArrayList`/`ArrayDeque` | 0.26–0.33× a native array | Each step returns a `{ value, done }` object and checks for concurrent modification. Use `forEach` (faster than native `Array.forEach`) or an indexed `get` loop. On maps, `map.forEach((k, v) => …)` was 1.5× faster than `for (const [k, v] of map)`. |
| string keys in `HashMap` / `LinkedHashMap` | 0.75–0.83× / 0.69× a native `Map` | Every call goes through the key-kind dispatch, and `LinkedHashMap` also keeps its list. Sparse integer keys (too spread out for the dense array) take the same path: 0.76×. If all keys are strings and you need neither value equality nor the `Map` interface, use a native `Map`. |
| `ArrayDeque` raw add/poll | 0.62–0.94× js-sdsl or mnemonist | Every add checks for `null` (the API requires it) and updates `modCount` for fail-fast iterators. Presize it: `new ArrayDeque(n)` really preallocates (up to 2^25 slots) and about doubles `addLast` throughput. `new ArrayList(n)`, `new HashMap(n)` and `new PriorityQueue(n)` only validate `n`. |
| `TreeMap` `get` and random `remove` | 0.93× and 0.79× js-sdsl | For read-mostly data, a sorted `ArrayList` with `Collections.binarySearch` is about 2.5× faster on `get`, 3.5× on `floor`/`ceiling` and over 10× on iteration. Use `TreeMap` when inserts and removals interleave with queries. |
| short streams (`findFirst`, `limit` on tiny inputs) | about 0.4× `Array.find` or a loop | A fixed setup cost per stream. For a single `find`, use `Array.find`. Prefer `mapMulti` over `flatMap` on hot paths: it does not create a stream per element. |
| `Collectors.toList`, `partitioningBy` | 0.74×, 0.87× native | The generic supplier/accumulator/finisher protocol. Use `stream.toList()` when you only need a list. |

For numeric pipelines, `IntStream`/`DoubleStream` (`mapToInt`, `IntStream.range`) are faster than `Stream<number>`
because of their specialised `sum()`, `average()`, typed-array `sorted()` and number `distinct()`: 2.3× on
`distinct + sorted`. Give hash keys a cheap `hashCode()`, since it runs on every lookup.

## Run it yourself

```sh
npm run bench:isolated                                    # the comparison above (needs a running Docker daemon)
npm run bench:isolated -- --only lru-cache,hashmap-get-int --reps 5
npm run bench                                             # in-process suite, every bench/*.bench.ts (several minutes)
npm run bench -- HashMap                                  # files whose name contains "HashMap"
npm run build && node bench/demo/index.js                 # HashMap.get vs a native Map
node bench/demo/index.js strings                          # the same with string keys
```

`bench:isolated` writes `bench/isolated/results.json`; `--only` replaces just the selected workloads. The in-process
suite (`bench/*.bench.ts`, `tinybench`) loads every library into one process and covers many more cases; it prints
ops/s, margin of error and the ratio to the fastest case per group, then a "Not fastest in" summary. `bench/demo`
runs the same `get` test on this library's `HashMap` and a native `Map`, each in its own Node process, and prints calls,
time, calls per second and nanoseconds per call.

For stable numbers, close heavy processes and plug in a laptop (throttling moves results by 10–20%), run a group two or
three times, and treat differences under about 10%, or within the printed `±%`, as noise.
